# Evaluations for the CSV-import agent (Phase 2)

This folder answers one question with numbers instead of opinions:

> Given a farm's spreadsheet, how well can something work out how to read it, how much human effort
> does that leave, and how often does it get something wrong **without anyone noticing**?

"Something" is called an **arm**. Today there is one real arm, the rule-based guesser that ships in the
app (`baseline`, **arm A**). Later a local AI model and judges plug in as more arms, and the same
numbers tell us whether they are worth their cost.

It is written in **Python** (standard library only; `pytest` for the tests). The importer itself stays
in TypeScript because the website runs it; Python calls the *real* importer through one small command
(`scripts/eval-bridge.ts`), so a score here is a score for the real code, not a copy.

## Run it

```bash
cd evals
python3 -m venv .venv && .venv/bin/pip install pytest      # once
.venv/bin/python -m pytest                                  # tests of the evaluation code (~15 s)
.venv/bin/python -m nhoma_evals.run build                   # regenerate the corpus (only if you change the generator)
.venv/bin/python -m nhoma_evals.run eval --arm oracle       # sanity: must be 100%
.venv/bin/python -m nhoma_evals.run eval --arm baseline     # ARM A
.venv/bin/python -m nhoma_evals.run eval --arm baseline --split test --save
```
Needs Node (already required by the app). Saved reports land in `results/`; raw per-file output goes to
`runs/` (git-ignored).

## How a file is scored

```
file bytes -> READ -> PROPOSE (arm) -> SCORE -> HUMAN -> IMPORT -> compare with the true pigs
```
1. **Read**: the real importer decodes and parses the bytes.
2. **Propose**: the arm sees only the headers and rows and proposes a *mapping* (which column feeds which
   field, plus how to read dates, numbers, sex words). It never sees the answer.
3. **Score**: compared with the true mapping. A mistake is **silent** if the app would not have flagged it
   for a person (a column quietly ignored, a pound weight read as kilograms...). Silent mistakes are the
   dangerous ones.
4. **Human**: the app lists what a person must settle. We play that person using the true answer. Two
   kinds are simulated, because the truth for a real farm lies between them:
   - **flagged**: fixes only what the app flags. Measures *silent risk*.
   - **diligent**: also studies the mapping screen and fixes every wrong column. Measures *effort*.
   The two "a human confirmed this" flags (`dateFormatConfirmed`, `numberFormatConfirmed`) are only ever
   set here. An arm can never set them.
5. **Import**: with the mapping the human ended with, the real importer translates and validates the
   rows (a dry run); every row is compared with the true pig.

## The test files (the corpus)

`corpus/` holds 100 generated files, each with an answer key (`<id>.truth.json`):
**80 Ghana-style** (English headers, day-first dates, period decimals, kilograms) and **20 stress**
(English, but month-first dates, pounds, European number style, semicolons, ragged rows, title lines,
unknown sex words, decoy columns like "Birth Weight"). Split 70/30 into **dev** and **test**: tune on dev,
report on test.

Everything is made by code from a seed (`corpus.py`), so the files can be regenerated byte for byte and a
test proves the committed files are current. The *pigs* and the *answers* come from code. A model never
invents an answer key.

### Assumptions you should challenge (all in `styles.py`)
- The proportions inside each category (how often a farm uses `dd/MM/yyyy`, how often a column is present,
  how many headers the baseline has never seen) are **my guesses**, not measurements. Replace them with real
  numbers as soon as there are real files.
- The only hard evidence so far: the real weekly report uses a two-digit year (`01/06/26`), which is why
  `dd/MM/yy` is in the corpus as a known gap.
- The "unseen" header list is written by me, so it is only as hard as my imagination. A proposer that
  aces it has beaten my list, not necessarily real farms.
- The simulated human is always correct and never gets tired.

## Reading the results (baseline, all 100 files)

| | |
|---|---|
| Headers the baseline was taught | **100%** mapped correctly |
| Headers it was **not** taught | **0%** (by construction: it only looks names up in a list) |
| Imports perfect if the human fixes only what is flagged | ~46% |
| ...if the human also checks every column | 100%, at ~3.7 actions per file |
| Files the importer cannot read at all today | 15 of 100 (date styles it has no name for, a title line above the headers) |

Do **not** quote the overall "60% of columns right" as the baseline's quality: it is mostly a
consequence of the unseen-header share assumed above. The **unseen** row is the target for an AI proposer.

## What this has already found

1. **Optional columns are dropped silently.** A weight, mother, father, notes or castrated column whose
   header the guesser does not recognise is simply ignored and the app does not say so. This is the main
   source of "imports with wrong pigs".
2. **A hole in the importer's own safety net (fixed).** A mapping that named a column the file does not
   have was reported as fine and silently read blank cells. A person cannot cause that, but a saved
   template meeting a changed file, or an AI inventing a header, can. The check now flags `unknownColumn`.
3. **Date styles the importer cannot read**: `dd-MM-yyyy`, `dd/MM/yy` (in the real report), `dd-MMM-yy`,
   `d MMM yyyy`. A closed set of transforms means no proposer can fix these; a new transform is needed.
4. A common header (`Mother ID`) was missing from the guesser's alias list.
